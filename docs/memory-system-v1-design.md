# Bloom 记忆系统 V1 设计草案

更新时间：2026-04-12

## 1. 目标

这份文档解决的是当前记忆系统的三个核心问题：

1. `shortTermSummary` 同时承担“近期摘要 / 当前状态 / 未完事项承载”三种职责，容易把角色卡死在旧场景里。
2. `longTermMemoryProfile` 目前是整段覆盖式文本，容易出现“覆盖丢失”和“短期内容误沉淀进长期”两种风险。
3. `memoryLibraryEntries` 同时被用户理解成“历史档案”和“当前生效记忆”，产品语义容易混乱。

V1 不追求一步到位做完整召回系统。V1 的目标是：

1. 先把当前系统从“字符串摘要堆叠”收稳。
2. 让短期层不再冻结角色。
3. 让长期层能修订、能保留历史、不无限膨胀。
4. 给后续更大的记忆系统升级预留稳定骨架，包括事件层、召回、检索、存储。

## 2. 当前代码现实

当前代码里的有效记忆入口主要是：

1. `Character.shortTermSummary`
2. `Character.longTermMemoryProfile`
3. `Character.memoryLibraryEntries`

相关代码：

1. [src/types.ts](../src/types.ts)
2. [src/services/memory/buildResolvedMemoryLayers.ts](../src/services/memory/buildResolvedMemoryLayers.ts)
3. [src/services/memory/autoLongTermRefreshPlan.ts](../src/services/memory/autoLongTermRefreshPlan.ts)

当前行为可以概括为：

1. `buildResolvedMemoryLayers()` 只是把 `shortTermSummary` 和 `longTermMemoryProfile` 取出来给主链读。
2. 开启自动刷新后，短期总结会按聊天条数间隔自动刷新，并写回 `shortTermSummary`，同时追加一条 `short-term` 记忆库记录。
3. 自动短期记录累计到阈值后，会自动刷新长期画像，并写回 `longTermMemoryProfile`，同时追加一条 `long-term` 记忆库记录。
4. 长期刷新成功后，当前实现不会自动清空短期，也不会自动压缩短期，更不会自动清理短期历史记录。

当前自动长期阈值：

1. 自动短期记录至少 `3` 条
2. 最新短期总结长度至少 `24` 字

这意味着当前系统更像：

1. 短期当前层：覆盖式
2. 长期当前层：覆盖式
3. 记忆库：追加式

问题是：

1. 短期层没有过期和降权语义。
2. 长期层没有“基于旧版修订”的机制。
3. 记忆库不是当前生效层，却很容易被产品感知成当前记忆本体。

## 3. V1 的分层原则

V1 建议把“当前生效记忆”和“历史档案”彻底分开。

### 3.1 `activeShortTermState`

定义：

当前仍在影响接下来几轮对话的短期状态层。

它不是：

1. 所有近期发生过的事
2. 短期历史档案
3. 场景镜头回放

它只应该承载：

1. 当前气氛
2. 当前关系余波
3. 当前未完回路
4. 当前临时限制
5. 最近的轻量变化方向

一句话理解：

这是角色“现在脑子里正挂着的几件事”。

### 3.2 `activeLongTermProfile`

定义：

当前生效的长期关系画像快照。

它不是：

1. 所有长期记录的简单拼接
2. 所有历史长期总结的全文合集
3. 最近一次短期总结的加长版

它应该承载：

1. 关系定位
2. 核心相处逻辑
3. 稳定偏好
4. 稳定边界
5. 长期触发点
6. 重要关系锚点

一句话理解：

这是角色当前对你们关系的长期版本理解。

### 3.3 `memoryLibraryEntries`

定义：

历史档案层。

它的用途是：

1. 回看
2. 导出
3. 审计
4. 调试
5. 手动整理

它不应该默认等于：

1. 当前正在生效的短期层
2. 当前正在生效的长期层

一句话理解：

这是记忆笔记本，不是角色此刻脑内全部展开的内容。

## 4. 短期层应该存什么

### 4.1 应该保留的内容

1. `currentAtmosphere`
   当前气氛。例：紧绷、刚缓和、带一点余怒、轻松。
2. `residualEffects`
   近期互动留下的余波。例：刚才的强势推进带来压迫感残留。
3. `openLoops`
   仍会影响后续几轮的未完回路，但必须结构化。
4. `recentShift`
   最近发生的短方向变化。例：饮食偏好话题已降温、互动重心转开。
5. `temporaryConstraints`
   当前临时边界或短期条件。例：用户未回应前，不默认继续推进刚才的冲突动作。

### 4.2 不该保留的内容

1. 冻结场景画面
2. 冻结动作镜头
3. 长篇事件复述
4. 过于具体的地点和姿态
5. 已经沉淀进长期的主体结论
6. 已经不再影响当前几轮的细节

不该写成：

1. “角色还在楼下”
2. “角色还在车里”
3. “角色随时准备上楼抓人”
4. “角色一直在等去吃火锅”

应该改写成：

1. 当前余波：刚才的强势推进仍带压迫感残留
2. 未完回路：是否继续推进，取决于用户下一步回应
3. 临时限制：用户未重新触发前，不默认延续旧场景动作

## 5. open loop 设计

“未完事项”不能只是自然语言句子，否则会让模型反复抓住旧话题。

V1 建议至少结构化成：

```ts
export type OpenLoopStatus =
  | 'active'
  | 'waiting_user'
  | 'dormant'
  | 'resolved';

export type OpenLoopCarryMode =
  | 'background_only'
  | 'resume_if_user_mentions'
  | 'can_gently_prompt';

export type ActiveOpenLoop = {
  id: string;
  topic: string;
  summary: string;
  status: OpenLoopStatus;
  priority: 'high' | 'medium' | 'low';
  carryMode: OpenLoopCarryMode;
  createdAt: number;
  lastTouchedAt: number;
  expiresAt?: number;
  resumeRule?:
    | 'only_if_user_reopens'
    | 'only_if_same_day'
    | 'only_if_same_scene'
    | 'allow_soft_check_in';
  sceneBound?: boolean;
};
```

### 5.1 字段解释

1. `status`
   决定这件事是否还能主动进入当前回复。
2. `priority`
   决定它在短期层里的权重。
3. `carryMode`
   决定角色后面是只带背景余波，还是可以轻提，还是只能等用户再提。
4. `expiresAt`
   决定它什么时候自动降权或失效。
5. `sceneBound`
   决定它是不是只绑定当前场景。

### 5.2 推荐语义

1. `active`
   当前仍强相关，允许影响接下来几轮。
2. `waiting_user`
   只能等用户重新提起，角色不主动展开。
3. `dormant`
   只是背景余波，不进入主回复。
4. `resolved`
   已结束，不进入当前短期层。

### 5.3 关键原则

不是“有未完事项就继续聊”，而是：

只有满足恢复条件，才允许继续承接。

例如：

1. 火锅话题如果用户没再提，只能是 `waiting_user + background_only`
2. 刚吵完架的情绪余波，可能是 `active + high`
3. 已离开旧场景的动作回路，应迅速转为 `resolved` 或直接过期

## 6. 长期层应该怎么更新

长期层既不能纯覆盖，也不能纯累积。

### 6.1 为什么不能纯覆盖

纯覆盖的风险：

1. 旧的重要信息被本次改写掉
2. 如果模型本次没写进去，就造成长期记忆缺失

### 6.2 为什么不能纯累积

纯累积的风险：

1. 会越来越长
2. 会出现矛盾并存
3. prompt 读取时会越来越脏
4. 角色容易同时带着“喜欢”和“不喜欢”两套结论

### 6.3 V1 的建议

长期层拆成：

1. `activeLongTermProfile`
   当前生效快照
2. `longTermHistoryEntries`
   长期版本历史档案

也就是：

1. 生效层允许覆盖
2. 历史层继续积累

### 6.4 正确的长期更新方式

不是“拿最新短期，直接把旧长期全文替换掉”。

而应该用三部分输入生成下一版长期快照：

1. 旧 `activeLongTermProfile`
2. 最近稳定下来的短期候选
3. 重要历史锚点

模型的任务应该是：

1. 保留仍然成立的长期理解
2. 修正已经变化的长期部分
3. 新增已稳定沉淀的新长期信息
4. 删除明显失效的旧长期判断

这本质上是“修订当前版本”，不是“从零重写”。

## 7. 长期层应该存什么

建议固定为较短、较稳的结构，避免无限增长。

例如：

1. `relationshipPositioning`
2. `coreInteractionLogic`
3. `stablePreferences`
4. `stableBoundaries`
5. `relationshipAnchors`
6. `changeNotes`

每节建议限制：

1. 2 到 4 句
2. 总字数上限
3. 用替换和修订代替无上限追加

## 8. 短期如何沉入长期

短期不能整体叠加进长期。

正确做法是：

先提炼，再沉淀。

### 8.1 允许进入长期的内容

1. 跨时间重复出现
2. 多次明确表达
3. 已被行为兑现
4. 明显影响关系和边界
5. 已稳定成相处模式

### 8.2 不应进入长期的内容

1. 一次性想法
2. 临时口味
3. 瞬时情绪
4. 旧场景画面
5. 需要用户再次触发才继续的轻量 open loop

### 8.3 火锅示例

错误写法：

1. 短期：用户想吃火锅
2. 长期：用户喜欢火锅
3. 短期又一直挂着等去吃火锅

正确写法：

1. 短期：饮食偏好话题已降温，若用户重提可继续
2. 长期：用户即时饮食偏好可能变化，不宜快速固化

如果后面反复出现“用户不想吃火锅”并且稳定成立，再修订长期层。

## 9. 自动刷新策略建议

### 9.1 自动短期刷新

保留当前按条数间隔触发的思路，但刷新目标不再是“写一整段摘要”，而是：

1. 更新 `activeShortTermState`
2. 生成一条短期历史档案记录

### 9.2 自动长期刷新

保留当前“累计一批短期后再进长期”的思路，但改成：

1. 输入旧长期快照
2. 输入最近一批短期候选
3. 生成新的长期快照
4. 追加一条长期历史版本记录

### 9.3 长期刷新成功后的短期处理

当前代码没有这一步，V1 建议必须补上。

长期沉淀成功后，短期层不应该原样保留。

应该做“轻压缩”：

1. 移除已经沉淀进长期的主体内容
2. 只保留 1 到 2 句仍在生效的余波
3. 保留低量的 `openLoops`
4. 删除冻结场景画面

这一步不是“清空短期”，而是“把短期从完整摘要压成当前状态”。

## 11. 迁移策略

V1 不需要一次性推翻现有实现，可以分 3 步迁移。

### 第一步：语义先分离

目标：

1. 保留现有 `shortTermSummary`
2. 保留现有 `longTermMemoryProfile`
3. 先在文案、生成规则和读取逻辑上，把它们分别逼近：
   - `activeShortTermState`
   - `activeLongTermProfile`

这一阶段重点：

1. 不再把短期写成场景冻结
2. 不再把短期临时等待写进长期
3. 长期刷新成功后，补短期轻压缩

### 第二步：结构化短期层

目标：

1. 新增结构化 `activeShortTermState`
2. 旧 `shortTermSummary` 仅作为兼容显示或导出文案

这一阶段重点：

1. 引入 `openLoops`
2. 引入过期和降权规则
3. 读取时优先用结构化短期层，而不是整段摘要

### 第三步：结构化长期层

目标：

1. 新增结构化 `activeLongTermProfile`
2. 长期历史版本单独保留

这一阶段重点：

1. 长期更新改成“基于旧版修订”
2. 长期结构固定，不无限增长
3. 为后续召回和检索提供稳定语义入口

## 12. 为完整记忆系统预留的后续层

当 V1 收稳以后，再继续做更大的记忆系统。

后续建议层次：

1. `event_log`
   原始事件层
2. `working_memory`
   当前短期生效层
3. `semantic_memory`
   长期语义层
4. `episodic_memory`
   可回看的事件型记忆
5. `retrieval_layer`
   按场景召回
6. `prompt_assembly`
   预算、优先级、去重、压缩

这样以后做：

1. 召回
2. 检索
3. 存储升级
4. 向量化
5. 混合检索

都不需要推翻 V1。

## 13. 下一步清单

### P0：先收当前系统

1. 收紧短期总结规则，禁止冻结场景画面进入短期当前层
2. 给短期“未完事项”增加最小结构化语义，至少先区分：
   - `active`
   - `waiting_user`
   - `dormant`
   - `resolved`
3. 长期刷新成功后，为当前短期层补“轻压缩”逻辑
4. 补短期 open loop 的过期和降权规则
5. 修复并稳定“手动刷新近期总结 / 生成长期画像”的接口兼容问题

### P1：把当前生效层结构化

1. 新增 `ActiveShortTermState` 类型和兼容生成逻辑
2. 新增 `ActiveOpenLoop` 类型和基础解析/生成逻辑
3. 新增 `ActiveLongTermProfile` 类型和基础修订逻辑
4. 让主链读取优先使用结构化层，字符串摘要退到兼容层

### P2：为完整记忆系统预留升级路径

1. 新增 `event_log` 概念和最小事件落盘策略
2. 为历史档案补 `sourceEventIds`
3. 设计 `semantic_memory / episodic_memory / retrieval_layer`
4. 规划后续召回预算、时间权重、相关度权重

## 14. 一句话结论

Bloom 记忆系统 V1 的核心不是“再写更长的总结”，而是：

1. 让短期层只保存当前仍生效的状态
2. 让长期层保存当前长期版本快照
3. 让历史档案只做历史档案
4. 让未完事项变成带状态、权重、恢复条件和过期规则的 open loop

只有这样，角色才不会一直卡在旧场景里，后面更大的召回和检索系统也才有稳定地基。

## 15. 与外部记忆方案的对照结论

下面这一节用于对照一套更完整的分层记忆方案，其核心特征包括：

1. `L0 / L1 / L2 / L3` 分层存储
2. 混合检索
3. 软边界 batch 切割
4. 记忆冲突版本链
5. 成本控制

这套思路整体是成熟且靠谱的，但它更像“完整记忆系统的中后期方案”，而 Bloom 当前 V1 更像“先把当前生效层收稳”的前置方案。

### 15.1 我认同的部分

#### 1. 分层存储必须做

这个判断成立。

原因：

1. 全量存档 + 现取现塞无法长期支撑大规模对话
2. 单纯摘要也会丢失大量细节和局部锚点
3. 不同记忆本来就应该走不同读取路径

Bloom 后续正式升级时，也应该明确至少有：

1. 原始事件层
2. 当前生效短期层
3. 当前生效长期层
4. 历史档案层
5. 检索召回层

#### 2. 提取比存储更难

这个判断非常重要。

真正困难的不是“把对话存起来”，而是：

1. 什么值得记
2. 记成什么粒度
3. 哪些东西应该影响当前几轮
4. 哪些东西应该沉入长期
5. 哪些东西应该直接丢弃或降权

这和 Bloom 当前碰到的问题高度一致。

#### 3. 混合检索是必须的

这个判断也成立。

纯关键词检索会漏掉大量语义近似、措辞变化、情绪表达和关系相似情境。后续如果 Bloom 做正式 recall，建议采用：

1. 关键词检索
2. 向量检索
3. 时间衰减
4. 关系相关性加权
5. 场景匹配加权

#### 4. 软边界切 batch 是正确方向

这个非常值得吸收。

固定消息数硬切容易把完整事件切断，造成：

1. 上半段在一个 batch
2. 下半段在另一个 batch
3. 事件链断裂
4. 提取结果变形

Bloom 后续如果做事件提取，应该优先用：

1. 时间间隔
2. 话题转折
3. 场景切换
4. 回合结束感

来做软边界切割，而不是只按固定条数切。

#### 5. 记忆冲突要有版本意识

这一点我也认同。

例如：

1. 用户以前喜欢 A
2. 后来明确改成 B
3. 系统不能把 A 和 B 同时当成当前有效结论

所以后续 Bloom 也应该支持：

1. 当前有效版本
2. 历史版本归档
3. 版本修订关系

#### 6. “完全记住一切”不是目标

这个观点我完全认同。

AI 陪伴产品记忆的重点不是存下所有句子，而是：

1. 记住真正会持续影响关系的东西
2. 记住关键锚点
3. 记住会改变角色判断的变化
4. 在 token 和成本有限的情况下做选择

### 15.2 我不完全认同，或者不建议直接照搬的地方

#### 1. 不建议把高层长期摘要长期整块常驻 system prompt

外部方案里有一类思路是把较高层摘要长期常驻在 prompt 中。

这个做法短期方便，但对 Bloom 这种强关系、强体感产品有几个风险：

1. 长期摘要会越来越重
2. 角色容易被固定成僵硬人格壳
3. 新变化进入长期层后的修订成本高
4. prompt 越来越像“携带厚重设定包”

Bloom 更合适的方式是：

1. 常驻的是“当前长期快照”
2. 不常驻的是“全部高层历史摘要”
3. 需要时再从历史层检索召回

换句话说：

常驻可以有，但必须短、稳、当前化。

#### 2. 单靠事件层和摘要层，不足以支撑 Bloom 的陪伴关系语义

外部方案更强调：

1. 事件
2. 摘要
3. 检索
4. 关键事实

但 Bloom 这种产品里，真正高频影响体验的往往不是单条事件，而是：

1. 当前气氛
2. 关系余波
3. 当前推进状态
4. 边界感
5. 角色该不该主动提某件事
6. 某件事现在只是背景，还是当前重点

所以 Bloom 必须单独保留：

1. `activeShortTermState`
2. `activeLongTermProfile`
3. `openLoops`

不能只靠“事件提取 + 检索命中”来决定当前回复。

#### 3. “未完事项”不能只是事件残留或一段普通摘要

这是 Bloom 和通用记忆系统差异最大的点之一。

如果系统只记：

1. 提过火锅
2. 没去成
3. 还没完成

那角色就会一直围着火锅打转。

如果系统只记：

1. 角色还在楼下
2. 角色还在车里
3. 随时准备上楼

那角色就会一直卡在上一幕。

所以 Bloom 的“未完事项”必须不是普通事件摘要，而是结构化的 `open loop`，至少包含：

1. 状态
2. 权重
3. 恢复条件
4. 过期规则
5. 是否绑定场景

这一层是我认为外部方案里没有被充分强调，但 Bloom 必须补强的部分。

#### 4. 检索强，不等于角色就自然

这一点必须明确。

检索只能解决：

1. 能不能找到
2. 找到什么

但不解决：

1. 找到之后该不该用
2. 用多重
3. 用户没提时该不该主动提
4. 当前关系阶段适不适合提
5. 当前场景是不是应该让旧话题退到背景层

所以 Bloom 的记忆系统不能只有：

1. 提取
2. 存储
3. 检索

还必须有：

1. 当前生效层
2. 权重层
3. 恢复条件层
4. 边界规则层

### 15.3 和 Bloom 当前方案的主要区别

外部方案更偏：

1. 全链路记忆工程
2. 大规模存储与检索
3. 召回和成本控制

Bloom 当前 V1 更偏：

1. 当前生效语义整理
2. 短期层不写脏
3. 长期层不误沉淀
4. 角色不被旧场景卡死
5. 生效层与历史档案彻底分离

所以两者不是互相排斥，而是阶段不同：

1. 外部方案像 Bloom 的正式记忆系统骨架
2. 当前 V1 像 Bloom 必须先补的地基

### 15.4 哪个更好

如果比较“完整度”和“工程成熟度”，外部方案更完整。

如果比较“是否适合 Bloom 当前直接全量落地”，答案是否定的。

Bloom 当前最需要保留并强化的是：

1. 当前短期生效层
2. 当前长期生效层
3. `openLoops`
4. 关系状态语义
5. 当前回复到底该受哪些状态影响

所以更好的方向不是二选一，而是融合：

1. 吸收外部方案的分层、检索、冲突更新、成本控制
2. 保留 Bloom 当前必须强调的 `active state + open loop + 边界语义`

### 15.5 推荐的融合方向

后续更完整的 Bloom 记忆系统建议做成：

1. `event_log`
   原始事件层
2. `memory_extraction`
   提取候选记忆
3. `activeShortTermState`
   当前短期生效层
4. `activeLongTermProfile`
   当前长期生效层
5. `memory_history`
   历史档案层
6. `retrieval_layer`
   混合检索与召回
7. `prompt_assembly`
   最终预算、去重、压缩和组装

其中最关键的差异化补充是：

1. `openLoops` 作为独立结构，不混在普通摘要里
2. 长期层使用“当前快照 + 历史版本”模式
3. 当前 prompt 优先吃当前快照，而不是厚重历史全文
4. 召回命中后仍要通过生效规则和边界规则过滤

### 15.6 本文档的立场

这份 V1 文档的立场不是否定更完整的分层检索方案，而是：

1. 认可它作为完整记忆系统骨架的价值
2. 明确 Bloom 当前不能跳过 active state 这一层
3. 明确 Bloom 当前最优先要解决的是“当前生效语义”而不是“更大规模检索”

一句话总结：

外部方案更像“强工程、强检索”的完整记忆架构；
Bloom 当前 V1 更强调“强关系、强状态、强生效语义”的基础层；
最终最优方向是两者融合，而不是二选一。
