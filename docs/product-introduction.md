# 小手机项目介绍

## 1. 项目概述

小手机不是一个单纯的 AI 聊天页面，也不是把大模型能力简单包装成对话框的工具型产品。
它更像一部被拟人化、被生活化的手机系统：用户打开的是一个手机容器，而这个容器里住着角色、关系、记忆、情绪和互动痕迹。

从体验目标上看，小手机想完成的不是“让 AI 回答问题”，而是“让用户拥有一部可以陪伴自己、回应自己、记录自己生活的手机”。
因此，它的核心不是单点聊天能力，而是把聊天、通讯录、动态、约会、情侣空间、音乐、论坛、钱包、监控、桌面自定义和小游戏等内容整合为一个统一的关系型世界。

这使它同时具有几层气质：

- 它是一个 AI 角色互动产品。
- 它是一个带手机桌面外壳的沉浸式容器。
- 它是一个轻恋爱模拟与陪伴产品。
- 它也是一个可持续扩展的互动娱乐世界。

## 2. 产品理念

### 2.1 把 AI 从“对话窗口”变成“生活空间”

传统聊天产品里，AI 往往只存在于聊天气泡里；当用户退出聊天页，体验就结束了。
小手机的理念是把 AI 角色从单一窗口中释放出来，让角色进入一个完整的生活空间。

在这个空间中，角色不只会回复消息，还会：

- 出现在通讯录和群聊关系里。
- 发布动态、参与评论和回复。
- 和用户进入约会场景，产生连续剧情。
- 在情侣空间里沉淀共同记录、感知和纪念内容。
- 与音乐、钱包、收藏、论坛等模块产生联动。

也就是说，小手机希望用户感受到的是“和一个角色共同生活在一部手机里”，而不是“向一个模型发出一次请求”。

### 2.2 用手机壳承载关系，而不是用功能堆叠替代体验

小手机选择“手机桌面”作为壳，不只是视觉包装，而是产品表达的一部分。

手机是用户最熟悉的数字生活入口：

- 桌面图标意味着不同的生活场景。
- 聊天、通讯录、动态、相册、音乐、钱包天然带有日常感。
- 页面的切换、历史记录的保留、桌面布局的自定义，会自然增强“这是我的设备”的拥有感。

因此，这个产品理念强调的不是功能越多越好，而是让每个模块都服务于“沉浸感、关系感、陪伴感、持续性”。

### 2.3 情绪、记忆和痕迹比单次回答更重要

小手机的设计并不只关注模型一次回复是否聪明，更关注长期体验中的以下三个维度：

- 情绪感：角色说话方式、互动节奏、关系氛围是否稳定。
- 记忆感：聊天、摘要、动态、约会记录、收藏是否能沉淀下来。
- 痕迹感：用户是否能在多个模块里看到曾经发生过的互动。

这也是为什么项目里会有摘要、动态生成、约会记录、收藏、情侣空间、论坛转发、持久化存储等设计。
这些能力共同构成了“关系会留下痕迹”的体验基础。

## 3. 产品定位与适用场景

从产品定位上看，小手机更接近“沉浸式 AI 关系终端”，而不是通用问答助手。

它适合的方向包括：

- AI 陪伴与情感互动产品。
- 角色扮演与世界观互动产品。
- 恋爱模拟与关系经营类体验。
- 拥有长期记忆和多模块联动的角色宇宙产品。
- 面向手机感、桌面感、生活流体验的 AI 娱乐应用。

它的价值不只是回答得像人，而是让用户逐步形成“我和这些角色共同生活在一个数字空间里”的感受。

## 4. 核心功能介绍

### 4.1 手机桌面与首页系统

首页不是普通导航页，而是整个产品世界的入口。

当前桌面系统支持：

- 手机桌面图标布局。
- Dock 区域与顶部导航卡片。
- 桌面分页。
- 桌面小组件展示。
- 根据设备容器尺寸自动计算布局。
- 高屏手机修正和不同宽度档位适配。

这一层决定了产品的第一感受：用户打开后看到的不是一个后台管理界面，而是一部有内容、有氛围、有角色入口的手机。

### 4.2 主应用壳

主应用壳承载核心生活流页面，目前主要分为四个主标签：

- 聊天
- 通讯录
- 动态
- 我的

这四个标签不是孤立页面，而是整个关系系统的主骨架：

- 聊天负责核心互动。
- 通讯录负责角色组织、好友关系和群聊管理。
- 动态负责角色生活感和公开互动感。
- 我的负责个人资料、角色管理、收藏、面具、世界书和数据管理。

### 4.3 聊天系统

聊天是小手机最核心的交互入口之一，但它已经不只是一个基础会话框。

当前聊天系统包含：

- 单聊与群聊。
- 流式 AI 回复。
- 角色设定驱动的回复生成。
- 按句拆分气泡，提升聊天拟真感。
- 文本、图片、位置、语音、转账等互动形式。
- 收藏、引用、转发、删除、复制、分享、回复预览等消息操作。
- 摘要与记忆整理能力。
- 通话记录等会话周边信息。

这套设计的重点在于，让聊天更接近真实社交软件里的关系互动，而不是只有“输入一段文本，得到一段文本”。

### 4.4 通讯录与社交关系组织

通讯录模块承担的是“角色关系结构化”的任务。

它支持的内容包括：

- 联系人浏览与搜索。
- 分组过滤。
- 新朋友页面。
- 群聊管理。
- 从联系人直接打开单聊。
- 从群聊列表进入群会话。

通讯录的价值在于，它让角色不再只是模型调用参数，而是成为“系统中的联系人”。
这种组织方式会显著增强用户对角色关系网络的感知。

### 4.5 动态系统

动态模块是小手机里非常关键的一层，因为它承担了“角色在聊天之外仍然活着”的体验。

目前动态系统具备：

- 角色动态发布。
- 动态评论与回复。
- 自动触发动态生成。
- 基于上下文的评论回复生成。
- 回退内容生成机制。

它的意义不只在于增加内容量，而在于让角色行为从私聊扩展到“公开痕迹”，从而增强世界感、真实感和持续性。

### 4.6 约会模块

约会模块是小手机中最具剧情感和关系推进感的部分之一。

它并不是简单弹出一个“约会页”，而是由完整的会话流程组成：

- 用户从聊天链路触发约会。
- 进入约会规划或恢复入口。
- 启动正式的约会场景页面。
- 基于消息流推进剧情和互动状态。
- 保存可继续的约会记录。
- 收藏重要约会内容。

约会场景中的消息不仅有普通文本，还可以携带叙事、状态、歌单等结构化信息。
这说明它已经从“专题页面”进化为一个带剧情控制和记录能力的互动子系统。

### 4.7 情侣空间

情侣空间是关系深化的重要模块，适合承载更长期、更私密、更沉淀式的内容。

当前方向包括：

- 双方互动记录。
- 感知视图。
- 共创内容与纪念内容沉淀。
- 更偏关系经营的专属空间体验。

如果说聊天是即时互动，动态是公共痕迹，那么情侣空间更像是长期关系资产的沉淀场。

### 4.8 音乐模块

音乐模块不是独立娱乐功能，而是关系氛围和沉浸体验的补充层。

当前系统中：

- 有独立音乐应用页面。
- 通过本地服务提供网易云相关代理接口。
- 支持歌曲、歌词、歌单详情等数据访问。

音乐能力使角色互动可以进一步延展到情绪氛围、共同歌单、场景配乐等方向。

### 4.9 钱包模块

钱包模块让产品的互动更接近真实社交与日常生活场景。

当前钱包页可承载：

- 卡片信息展示。
- 交易记录展示。
- 与聊天中的转账等互动形式形成联动。

它的产品价值不在于金融能力本身，而在于增加“真实生活系统”的质感。

### 4.10 论坛模块

论坛模块补足了“公开内容互动”的另一层。

与动态相比，论坛更适合：

- 话题性内容。
- 帖子结构化浏览。
- 分享与转发场景。
- 更偏社区感的互动空间。

这使小手机不仅有私域关系，也具备一定程度的公共讨论空间。

### 4.11 监控模块

监控模块提供了另一种观察手机状态与界面的方式，包含独立的手机界面视图。
它在产品上强化了“这是一部设备”的感受，而不仅仅是若干页面的拼合。

### 4.12 自定义与视觉系统

小手机非常重视“这部手机是不是我的”这件事，因此视觉自定义不是边缘功能，而是核心能力之一。

当前可自定义内容包括：

- 全局背景。
- 桌面图标配置。
- 小组件配置。
- 顶部导航栏样式。
- 聊天气泡样式。
- 动态卡片样式。
- 字体、圆角、透明度、缩放等视觉参数。
- 全局自定义 CSS。
- 数据导入导出。

这意味着小手机不是固定样式的壳，而是一套可以持续打磨个性表达的视觉系统。

### 4.13 游戏中心

小游戏模块提升了轻娱乐性和陪伴感，当前已经包含多种游戏类型，例如：

- 五子棋
- 贪吃蛇
- 真心话大冒险
- 石头剪刀布
- 连连看
- 卡牌对决
- 情侣问答

这些游戏不是孤立的附加内容，它们可以成为角色互动和关系推进的一部分。

## 5. 体验设计特点

小手机之所以有区别于普通 AI 产品的感觉，核心来自以下几个设计特点。

### 5.1 统一手机容器

所有功能尽量收拢在同一个手机容器中，包含：

- 页面切换。
- 弹窗与确认框。
- 聊天浮层。
- 游戏卡片与论坛内容。

这样做的目的，是避免浏览器原生界面打断沉浸感，维持“始终在手机里”的体验一致性。

### 5.2 多模块联动

一个角色不是只存在于聊天页，而会同时出现在：

- 通讯录
- 群聊
- 动态
- 约会
- 情侣空间
- 收藏和分享行为

这种联动使角色不再像一个孤立功能，而更像一个持续存在的人物。

### 5.3 重视持久化和可恢复性

小手机不是一次性体验产品。
聊天历史、约会记录、动态数据、视觉配置、用户资料等内容会被持续保存，从而支持长期使用和逐步沉淀。

### 5.4 支持深度个性化

从角色、面具、世界书到视觉样式、桌面布局、聊天外观，小手机允许用户塑造自己的关系世界与设备风格。

## 6. 技术方案介绍

## 6.1 前端技术栈

项目当前以前端应用为主，核心技术栈包括：

- React 19
- TypeScript
- Vite
- Tailwind CSS 4
- `motion/react` 动效库
- `lucide-react` 图标库

这套组合的特点是：

- React 负责组件化和状态驱动页面。
- TypeScript 负责类型约束和复杂业务模型管理。
- Vite 提供开发期快速启动与构建能力。
- Tailwind CSS 4 提供样式组织基础。
- `motion/react` 用于页面和面板级动画表现。

同时，从依赖上看，项目还接入了以下能力：

- `@google/genai` 用于 Gemini 模型调用。
- `react-easy-crop` 用于图片裁剪类交互。
- `qrcode.react` 用于二维码场景渲染。
- `express` 用于本地开发服务和代理层。
- `better-sqlite3` 已进入依赖体系，为后续更强本地数据能力保留空间。

## 6.2 应用结构

项目当前不是简单的单页应用，而是“顶层壳 + 功能域拆分”的结构。

核心结构可以概括为：

- `src/App.tsx` 仍是顶层状态中心和应用切换入口。
- `src/components` 承担页面和业务 UI。
- `src/features` 承担更明确的领域拆分。
- `src/services` 承担 AI、动态生成、消息操作等服务逻辑。

这种结构说明项目已经从“全部逻辑堆在一个文件”逐步进入“按功能域拆分”的阶段。

如果按技术职责进一步概括，当前结构可以分成五层：

- UI 展示层：负责页面渲染、交互反馈和手机壳体验。
- 页面容器层：负责页面装配、参数传递和模块衔接。
- 业务运行时层：负责聊天、群聊、约会、动态等实际执行逻辑。
- 服务层：负责 AI 调用、Prompt 构建、消息操作、内容生成和触发编排。
- 持久化层：负责本地配置、资源、历史记录和业务数据存储。

这种分层的好处是，产品虽然功能复杂，但每一层的职责开始逐渐清晰，后续继续拆分时不会完全失控。

## 6.3 顶层状态与数据组织

当前顶层状态仍主要由 `src/App.tsx` 持有，负责控制：

- 当前激活的应用页。
- 主壳 tab 状态。
- 当前选中的角色和群聊。
- 设置中心。
- 顶层业务数据。
- 应用内对话框与弹层总线。

主要业务数据集中在 `appData` 中，包含：

- 角色数据
- 聊天历史
- 用户资料
- 收藏与面具
- 世界书
- 动态数据
- 情侣空间数据
- 好友申请
- 群聊
- 通话记录
- 已保存约会与已收藏约会
- 音乐数据
- 钱包数据
- 视觉设置

这套组织方式的优点是整体联动方便，缺点是顶层状态体量较大，因此项目也在持续向 feature 化和域边界清晰化演进。

从数据流角度看，当前项目主要是典型的前端主导架构：

1. 用户在手机壳内触发交互。
2. 页面组件把事件传给容器层和运行时层。
3. 运行时层决定是否调用 AI、是否写入聊天记录、是否触发动态或约会状态更新。
4. 更新后的业务数据回写到顶层状态和本地持久化链路。
5. UI 根据状态变化立即重渲染。

这让项目具备比较强的前端交互响应能力，也适合沉浸式、页面切换频繁的产品形态。

## 6.4 AI 调用架构

小手机的 AI 能力已经不是零散分布，而是逐步收口到统一运行时。

当前 AI 调用层的特点包括：

- 支持 Gemini。
- 支持 OpenAI 兼容接口。
- 通过统一的运行时客户端发起请求。
- 将模型配置集中到配置列表和激活配置中管理。

统一配置项主要包括：

- provider
- model
- baseUrl
- apiKey
- temperature

在此基础上，聊天、群聊、摘要、动态生成、评论回复、约会、情侣空间等多个入口已经逐步接入统一 AI 运行时。

从实现细节看，`runtimeClient` 当前已经承担了统一入口职责：

- 自动判断当前配置是 Gemini 还是 OpenAI 兼容接口。
- 统一做 API Key、Base URL、Model 等配置校验。
- 同时支持普通文本生成和流式生成。
- 将不同供应商的消息结构做适配转换。

这层统一非常关键，因为它把上层业务从具体供应商差异里解放了出来。对业务模块来说，更关心“要什么内容”和“在什么场景生成”，而不是“不同平台接口怎么拼”。

## 6.5 Prompt 体系

项目中的 Prompt 不是单个模板，而是按场景拆分维护的体系。

当前已拆分的方向包括：

- 普通聊天 Prompt
- 群聊 Prompt
- 摘要 Prompt
- 动态生成 Prompt
- 动态评论回复 Prompt
- 约会 Prompt

这种拆分方式适合复杂产品，因为不同场景对角色语气、输出结构、记忆引用和行为规则的要求并不相同。

从工程角度看，Prompt 体系承担了三个关键任务：

- 把角色设定、世界书、面具、上下文组织成模型可消费的输入。
- 把不同场景的行为规则显式化，降低提示词相互污染。
- 为摘要、动态、约会等结构化场景保留稳定输出约束。

这意味着 Prompt 在项目里不是临时文案，而更像“AI 行为规则层”。

## 6.6 聊天运行时分层

聊天链路已经从过去直接内嵌在 `App.tsx` 中，逐步拆成更清晰的层次，包括：

- 挂载层
- 会话容器层
- 会话展示层
- 运行时层
- 运行时核心层

这样做的意义在于：

- 让单聊和群聊可以共享部分基础能力。
- 让 UI 逻辑和 AI 运行逻辑逐步解耦。
- 为后续继续抽象更高层共享运行时打基础。

其中运行时核心层已经具备一部分通用控制能力，例如：

- 统一维护生成中状态。
- 管理当前有效 generation id。
- 防止旧请求结果覆盖新请求状态。
- 统一收口运行时错误。

这类设计对于流式输出和频繁切换会话尤其重要，可以减少并发请求造成的状态错乱。

## 6.7 动态系统的服务化

动态模块当前已经具备比较明确的服务层结构，分为：

- 触发层
- 生成层
- 编排层

这代表动态能力已经不只是页面渲染逻辑，而是拥有较清晰的业务规则组织方式，便于继续扩展自动发布、评论策略和上下文触发机制。

例如当前动态编排层已经具备这样的链路能力：

- 判断用户输入是否显式触发动态发布。
- 判断聊天上下文是否应该自动触发角色发动态。
- 生成聊天内回应文本。
- 生成真正要发布的动态内容。

这让动态系统从“手动点按钮发布内容”升级为“角色行为的一部分”。

## 6.8 浏览器持久化体系

小手机非常重视本地长期保存能力，因此项目中已经建立了较完整的持久化基础设施。

当前持久化层包含：

- 本地配置存储。
- 浏览器数据库封装。
- 资源持久化服务。
- Object URL 管理。
- 不同业务数据的 store 与 bridge。

目前已经覆盖和延展到的内容包括：

- 聊天历史
- 约会记录
- 通话记录
- 动态数据
- 情侣空间数据
- 音乐数据
- 钱包数据
- 用户资料
- 论坛数据
- 好友申请
- 聊天组织结构
- 视觉设置

这套设计的意义在于，用户不是每次刷新后重新开始，而是可以把这部“手机”真正养起来、用下去。

其中资源存储层已经通过浏览器 IndexedDB 建立了基础设施，用于保存图片和文件类资源，并支持：

- 以对象存储方式写入资源。
- 按 id 读取资源。
- 删除资源。
- 列出已保存资源。
- 为资源增加来源、时间戳、文件名、原始地址等元信息。

这类能力对头像、背景图、聊天素材、用户上传图片等场景都很关键。

## 6.9 视觉资源与自定义配置

视觉系统已经不只是几组颜色变量，而是一个覆盖桌面、聊天、动态和导航栏的统一配置对象。

`VisualSettings` 当前承载的内容很丰富，包括：

- 桌面图标配置
- 小组件配置
- 顶栏配置
- 桌面布局和字体配置
- 聊天气泡和头像配置
- 动态卡片配置
- 全局背景与全局 CSS

这说明项目在技术上已经把“视觉个性化”当成一级能力，而不是临时拼接功能。

换句话说，视觉系统已经具备“配置驱动 UI”的雏形：

- 页面外观不完全由写死样式控制。
- 很多桌面和聊天表现可以由数据对象驱动。
- 视觉调整可以被保存、恢复、导出和迁移。

这对于强调“我的手机”“我的风格”的产品来说，是非常有价值的技术基础。

## 6.10 本地开发服务与代理能力

项目不是纯静态前端，开发期通过 `server.ts` 提供本地服务。

当前服务端职责包括：

- 启动 Express + Vite 的开发服务器。
- 提供健康检查接口。
- 提供网易云音乐相关代理接口。
- 在生产环境下托管前端构建产物。

音乐相关代理能力目前包含：

- 歌曲播放地址代理
- 歌词数据获取
- 单曲详情获取
- 歌单详情获取

这使前端页面在音乐体验上具备更完整的可用性。

当前 `server.ts` 的作用可以理解为“本地 BFF”：

- 对前端隐藏第三方接口细节。
- 处理一部分跨域和请求头问题。
- 为音频流、歌词和歌单查询提供中转。
- 在开发环境中同时托管前端和接口服务。

对于这种手机型产品来说，这样的服务层可以让前端模块更专注于体验本身。

## 6.11 类型系统

由于项目业务复杂，类型系统在整体开发中占有很重要的位置。

当前核心类型覆盖：

- 角色
- 聊天消息与聊天历史
- 视觉配置
- 约会会话
- 通话记录
- 钱包数据
- 小组件和桌面图标
- 好友申请与群聊组织

这类类型定义为复杂业务提供了更稳定的结构基础，也使模块拆分更可控。

随着模块增多，类型系统的意义会越来越明显：

- 它帮助不同模块共享同一套业务模型。
- 它减少聊天、动态、约会等多链路并行开发时的结构分歧。
- 它为后续继续做领域边界拆分提供了基础。

从维护角度说，小手机这种产品如果没有比较完整的类型约束，后期复杂度会迅速失控。

## 6.12 关键技术亮点总结

如果把技术方案压缩成几个最值得强调的点，小手机当前的技术亮点主要有：

- 采用 React + TypeScript + Vite 构建复杂前端交互壳，保证开发效率和页面响应速度。
- 以统一 AI 运行时兼容 Gemini 与 OpenAI 兼容接口，降低模型切换成本。
- 以场景化 Prompt 体系支撑聊天、摘要、动态、约会等多种互动模式。
- 以运行时分层和服务层拆分控制聊天链路复杂度。
- 以本地持久化体系保存历史记录、资源和配置，支撑长期使用。
- 以配置化视觉系统支持桌面、聊天和动态等多模块个性化。
- 以 Express 本地服务作为前端能力补充，支撑音乐代理和开发集成。

## 7. 当前架构阶段判断

从现状来看，小手机已经不是“做 Demo”的阶段，而是一个主线功能已经非常完整的项目。

当前状态可以概括为：

- 手机壳和多应用框架已经成型。
- 聊天主链已经具备较高完成度。
- 约会、动态、情侣空间、音乐、钱包、论坛等模块已形成体系。
- 持久化与视觉自定义具备较强基础。
- AI 调用链已经明显统一化。

同时，项目也有一些现实中的架构特征：

- `App.tsx` 仍然偏大，顶层装配压力较重。
- 角色域的边界还可以继续细化。
- 单聊与群聊运行时还可以继续向更高层共享能力收敛。
- 一些历史文件还残留中文乱码问题。

这说明项目已经从“有没有”阶段进入“怎么继续做得更稳、更清晰”阶段。

## 8. 项目优势总结

如果从产品和工程两个角度一起看，小手机的主要优势包括：

- 产品表达鲜明，不是普通 AI 聊天壳。
- 手机容器与角色世界的结合度高，沉浸感强。
- 功能模块完整，生活感和关系感较强。
- 支持长期记忆、记录沉淀和多模块联动。
- 视觉自定义能力强，个性化空间大。
- AI 运行时、Prompt 和持久化已经具备结构化基础。

## 9. 后续可继续强化的方向

如果后续继续迭代，小手机最值得优先推进的方向包括：

- 继续拆分角色域，建立更明确的角色持久化和写入边界。
- 继续降低 `App.tsx` 的顶层复杂度。
- 进一步统一单聊与群聊运行时抽象。
- 深化角色与动态、论坛、情侣空间、群聊之间的联动规则。
- 优化说明文档、类型命名和历史乱码内容，提升可维护性。

## 10. 一句话总结

小手机的核心价值，不是“提供一个会说话的 AI”，而是“把 AI 角色、关系记忆和生活痕迹装进一部可被拥有、可被定制、可被持续使用的手机里”。
