# 商城 App 完整设计方案

## 1. 文档目的

这份文档用于把 Bloom 的 `商城 App` 从“一个想做的独立功能”整理成一份可执行、可分批实现、可继续扩展的完整方案。

它要回答的核心问题是：

1. 商城到底是什么，它在 Bloom 里承担什么角色
2. 商城一共要做什么，哪些是第一批必须做，哪些可以后做
3. 支付、订单、物品归属、送货、送礼这些交易后果怎么落地
4. 商城怎么和聊天、钱包、情侣空间、动态、监控等已有模块联动
5. 商城除了“像淘宝一样能买东西”之外，还能有什么更好玩的玩法

---

## 2. 产品定位

### 2.1 结论

Bloom 的商城不是聊天页里的一个附属面板，也不是普通电商壳子。

它应该是一个和 `论坛`、`情侣空间`、`钱包`、`音乐` 同级的独立 App，定位为：

**一个把购物、送礼、共同生活和角色互动接在一起的生活消费场景。**

它的目标不是只让用户“下单”，而是让商品变成关系中的实际事件：

1. 我为自己买了什么
2. 我给 TA 送了什么
3. TA 明确喜欢什么、嫌弃什么、会嘴硬收下什么
4. 哪些东西会进入背包、衣柜、共同空间和后续聊天

### 2.2 一句话定义

> 商城 App 是一个以“标准购物骨架 + 角色互动层 + 支付/订单/物品归属 + 跨模块后续”为核心的独立生活化应用。

---

## 3. 为什么必须做成独立 App

商城不应该长成：

1. 聊天页底部的一个小抽屉
2. 钱包里的一个二级页面
3. 情侣空间里的一个购物入口

而应该长成：

1. 首页可直接点击进入的独立应用
2. 有自己的搜索、分类、详情、购物车、订单、物品页
3. 有自己的推荐逻辑、送礼逻辑、配送逻辑和互动逻辑

原因很简单：

1. 购物是完整行为链，不是单个按钮
2. 商品需要支付、订单、状态和归属
3. 商城未来会承载送礼、共逛、共同空间陈列、愿望单、到货余波等玩法
4. 它应该是 Bloom 世界里的生活模块，而不是聊天的“附属工具”

---

## 4. 核心原则

### 4.1 骨架标准化

商城的基础使用方式必须熟悉，用户一眼就会用。

必须保留：

1. 搜索
2. 分类
3. 双列商品流
4. 商品详情
5. 购物车
6. 订单
7. 我的物品

### 4.2 差异化不靠魔改布局

Bloom 的差异化不应该靠“把商城首页做得很怪”，而应该靠：

1. 角色点评
2. 一起逛模式
3. 分享给角色
4. 送礼反馈
5. 购买后余波

### 4.3 商品要有后果

在 Bloom 里，一次购买不能只停留在“支付成功”。

商品应该至少流向以下一个去处：

1. 我的物品
2. 我的衣柜
3. 我的道具
4. 送礼记录
5. 共同空间陈列
6. 数字解锁

### 4.4 商城必须和钱包打通

商城不单独造支付体系，统一用钱包付款。

### 4.5 生成要可控

商城不应纯靠模型自由生成。

正确做法是：

1. 静态底库提供可控商品
2. 搜索和刷新先召回静态商品
3. 不足的部分再按类目和标签受控补货
4. 模型主要负责补充货架、生成短评、重排结果和共逛氛围

## 6. 商城信息架构

### 6.1 顶层导航

商城底部导航固定为：

1. `首页`
2. `购物车`
3. `订单`
4. `物品`

### 6.2 首页顶部模式切换

首页顶部固定模式切换：

1. `自己买`
2. `送给TA`
3. `一起逛`
4. `私密专区`

### 6.3 首页结构

```text
搜索栏
模式切换
一级类目入口
本轮货架主题
今日推荐商品流
角色点评位
快捷入口：愿望单 / 最近看过 / 共同空间
```

### 6.4 商品详情页结构

```text

角色点评

```

底部动作栏固定为：

1. `加入购物车`
2. `立即购买`
3. `问问TA`
4. `送给TA`

5. 礼物
6. 睡眠
7. 私密
8. 情侣
9. 共同空间

男装：

1. T 恤
2. 衬衫
3. 外套
4. 裤装
5. 居家服

女装：

1. 上衣
2. 裙装
3. 居家服
4. 配饰
5. 外套

家居：

1. 香薰
2. 灯具
3. 杯具
4. 床品
5. 摆件

私密：

1. 私密穿搭
2. 私密用品
3. 氛围辅助
4. 护理清洁
5. 情侣礼盒

共同空间：

1. 桌面摆件
2. 灯光氛围
3. 相框挂饰
4. 纪念物
5. 共用生活用品

### 7.3 标签体系

每个商品至少带这些标签：

1. 风格标签
2. 场景标签
3. 关系标签
4. 价格带
5. 敏感等级
6. 去向标签

### 7.4 商品图片策略

每个商品都必须有可显示的视觉资源，不能出现“只有标题没有图”的情况。

视觉资源优先级建议固定为：

1. `受控生成的扁平插画`
2. `品类图标或 pictogram`
3. `emoji 兜底`

默认原则：

1. 当前前提是 **没有本地静态商品图**，所以第一批不能依赖真实商品图资源
2. 第一批首页推荐位、商品详情页、重点礼物位优先使用 `扁平插画 / icon + 背景卡片`
3. 私密专区也应该有图片，但更适合使用包装图、材质图、轮廓图、扁平插画，不要让展示层过于直白
4. 同一类商品的视觉风格应统一，不要混用写实照片、廉价素材图和系统 emoji
5. 如果某个商品暂时没有正式插画，就必须至少有 `icon 或 emoji + 统一背景模板`

建议每个商品最少准备：

1. `coverImage`
2. `thumbnailImage`
3. `fallbackIcon`
4. `fallbackEmoji`

第一批落地建议：

1. 不做“等待以后补图再上线”的策略
2. 第一批全部允许使用 `统一模板卡面`
3. 统一模板卡面由以下元素构成：
   - 一个大图标或插画
   - 一组固定背景渐变
   - 一个类目色
   - 一个小 emoji 或角标
4. 暂时没有正式插画的商品先走 `icon + 纯色底 / 渐变底`
5. 再不行才使用 emoji

也就是说：

**emoji 可以有，但不应成为商城主视觉；第一批主视觉应是“统一模板卡面”。**

它更适合：

1. 加载失败兜底
2. 小标签角标
3. 类目入口
4. 购物车和订单中的小型占位

第一批推荐的现实策略是：

1. 类目入口使用 `icon + emoji`
2. 商品流使用 `统一模板卡面`
3. 商品详情页顶部使用 `放大版模板图`
4. 后续如果有条件，再逐步替换成更完整的插画或正式商品图

### 7.5 商品文字描述体系

每个商品不能只有标题，必须有多层级文案。

建议分成 5 层：

1. `title`
2. `subtitle`
3. `cardBlurb`
4. `detailDescription`
5. `recommendationReason`

它们分别承担的作用：

`title`

1. 商品名
2. 用于搜索命中
3. 长度短，适合卡片

`subtitle`

1. 补充风格、材质、场景
2. 用于商品卡第二行

`cardBlurb`

1. 一句短描述
2. 告诉用户这是什么感觉、适合什么场景
3. 适合首页和搜索结果流

`detailDescription`

1. 商品详情的主体文案
2. 要足够详细，不能只是标题复述
3. 至少应该写清楚外观、材质、使用场景、适合谁、会被放到哪里

`recommendationReason`

1. 为什么此刻推给用户
2. 为什么适合送礼、自己买或放进共同空间
3. 可以结合用户近期选择、搜索偏好和角色关系状态生成

详细描述建议至少覆盖这些内容：

1. 这件物品看起来是什么样
2. 摸起来或材质上有什么感觉
3. 更适合什么场景
4. 适合自己买还是送礼
5. 买完后会进入哪里
6. 如果送给角色，后续会发生什么类型的反馈

商品卡上不必显示全部长文，但详情页必须能展开查看完整描述。

## 8. 四种商城模式

### 8.1 为自己买

定位：标准购物模式。

特点：

1. 更强调个人偏好和最近搜索
2. 支持普通购买和加入购物车
3. 购买后主要进入 `我的物品`

### 8.2 送给 TA

定位：礼物模式。

特点：

1. 商品流优先展示更适合送礼的商品
2. 更强调角色喜好和关系阶段
3. 详情页突出 `收下概率 / 喜欢概率 / 后续反应`

### 8.3 一起逛

定位：和某个角色共同浏览商城。

特点：

1. 用户选择一个角色作为本轮陪逛对象
2. 刷新一次货架时，一起生成：
   - 一批商品结果
   - 本轮货架主题
   - 角色对少量商品的即时看法
3. 不要求每个商品都说话，只点评最相关的几件

### 8.4 私密专区

定位：受限展示的隐私购物区。

特点：

1. 单独入口
2. 单独气质
3. 单独推荐逻辑
4. 默认隐私浏览

这里仍然走标准商城结构，但类目、推荐和交互语气更克制、更私密。

## 9. 支付方案

### 9.1 统一走钱包

商城所有订单都必须走 `walletData` 扣款，不单独新建支付体系。

### 9.2 支付流程

1. 用户选择商品
2. 选择购买去向
3. 进入确认订单页
4. 选择付款卡
5. 确认支付
6. 钱包扣款
7. 商城创建订单
8. 钱包增加流水

### 9.3 钱包流水分类建议

1. `mall_purchase`
2. `gift_purchase`
3. `digital_unlock`
4. `mall_refund`

### 9.4 第一版支付能力

第一版只做：

1. 选卡付款
2. 余额不足拦截
3. 支付成功写流水
4. 退款原路退回

不做：

1. 多卡混付
2. 优惠券
3. 积分抵扣
4. 外部支付网关

## 10. 订单和送货方案

### 10.1 订单去向

下单时必须先明确商品要送到哪里。

支持 4 种去向：

1. `送到我这里`
2. `直接送给TA`
3. `送到共同空间`
4. `数字立即发放`

### 10.2 送到我这里

适用于普通实物、自用商品。

状态流转：

`待付款 -> 已付款 -> 备货中 -> 已发货 -> 派送中 -> 已签收`

签收后：

1. 进入 `我的物品`
2. 如果是穿戴类，归入 `我的衣柜`
3. 如果是消耗/使用类，归入 `我的道具`

### 10.3 直接送给 TA

适用于礼物。

状态流转：

`待付款 -> 已付款 -> 备货中 -> 已送达给TA -> TA已签收 -> TA已拆开 -> 已反馈`

完成后：

1. 不进入用户自持物品
2. 进入 `送礼记录`
3. 触发角色反应
4. 某些商品可继续进入共同空间

### 10.4 送到共同空间

适用于摆件、纪念物、共用品。

状态流转：

`待付款 -> 已付款 -> 配送中 -> 已到空间仓库 -> 已摆放`

完成后：

1. 不进入普通背包
2. 进入 `共同空间陈列`
3. 可在情侣空间中决定摆放位置或启用状态

### 10.5 数字立即发放

适用于主题、气泡、头像框、贴纸包等数字商品。

状态流转：

`待付款 -> 已付款 -> 已发放`

完成后：

1. 直接解锁
2. 无物流
3. 无签收

### 10.6 订单页必须有的能力

1. 查看订单状态
2. 查看物流时间线
3. 取消未发货订单
4. 申请退款
5. 查看送礼反馈
6. 再买一次

## 11. 购买后的物品放在哪里

### 11.1 正式归属不要挂在 Monitor 上

`MonitorApp` 的 `inventory` 更像一个投影展示位，不应该作为商城资产主存储。

商城应该有独立资产区：

1. `我的物品`
2. `我的衣柜`
3. `我的道具`
4. `送礼记录`
5. `共同空间`

### 11.2 我的物品

存放普通实物、收藏品和已签收但不属于衣柜/道具的商品。

### 11.3 我的衣柜

存放穿搭类商品。

后续可扩展：

1. 用户展示
2. 试穿预览
3. 角色评价

### 11.4 我的道具

存放可使用、可消耗、可触发效果的商品。

后续可扩展：

1. 使用后触发聊天
2. 使用后触发场景
3. 使用后变更状态

### 11.5 送礼记录

存放“我买来送给角色”的商品，不和自有物品混在一起。

记录字段包括：

1. 送给了谁
2. 何时送达
3. TA 如何反馈
4. 是否后续提起

### 11.6 共同空间

存放已送到情侣空间或共同空间的商品。

后续可直接联动：

1. 情侣空间展示位
2. 共同空间账本
3. 共同动态

## 12. 角色互动方案

### 12.1 问问 TA

定位：商城页内即时互动。

特点：

1. 不跳走
2. 快速得到一句到几句角色反馈
3. 适合轻判断

### 12.2 分享给 TA

定位：把商品带进聊天深聊。

特点：

1. 点击后跳转聊天页
2. 自动带入商品卡
3. 用户可以继续追问

### 12.3 一起逛

定位：共逛场景。

一次刷新一起生成：

1. 当前货架主题
2. 商品结果
3. 陪逛角色态度
4. 角色对少量商品的短评

### 12.4 送礼反馈

这是最重要的互动链之一。

送礼反馈不应该只有一句话，而应该至少包含：

1. 收不收
2. 喜不喜欢
3. 嘴硬还是直接承认
4. 会不会后续再提起
5. 会不会放进共同空间

---

## 13. 搜索、刷新与生成规则

### 13.1 搜索不是直接生成文案

搜索首先要被解析成结构化意图：

1. 一级类目
2. 二级类目
3. 风格
4. 场景
5. 价格带
6. 是否送礼
7. 是否私密

### 13.2 刷新逻辑

刷新时建议生成 4 类内容：

1. 本轮货架主题
2. 一批商品结果
3. 角色点评位
4. 推荐排序变化

### 13.3 受控生成流程

1. 解析用户输入
2. 静态底库召回
3. 不足时按类目模板补货
4. 结合用户偏好、角色偏好和模式重排

---

## 14. 还有什么更好玩的玩法

这是商城除了“能买东西”之外最值得加分的部分。

### 14.1 今日货架主题

每次进商城不是死板首页，而是有一轮主题：

1. 今晚适合慢慢挑
2. 更适合买礼物
3. 睡前氛围
4. 共同空间补货

### 14.2 角色愿望单

角色不是被动收礼，而是可以逐渐露出偏好：

1. 明示喜欢什么
2. 暗示想要什么
3. 收藏夹里留下痕迹

### 14.3 陪逛情绪条

一起逛时显示陪逛状态，例如：

1. 今天很爱管你买什么
2. 明显更适合送礼
3. 这轮嘴上嫌弃但在认真看

### 14.4 到货开箱

某些商品到货后不只是“已签收”，而是可以触发：

1. 开箱小弹层
2. 角色评价
3. 共同空间摆放确认

### 14.5 套装收集

某些商品可以属于同一主题套装：

1. 收集到一定数量解锁额外反馈
2. 放进共同空间时有组合效果

### 14.6 节日礼物建议

在纪念日、节日、关系节点上，商城自动给出合适货架。

### 14.7 情侣任务

例如：

1. 一起挑一件放进共同空间的东西
2. 给 TA 选一件本周礼物
3. 用预算完成一轮共同采购

### 14.8 论坛外溢玩法

后续可扩展：

1. 匿名发帖问大家送礼建议
2. 晒到货
3. 围观他人搭配

## 15. UI 设计方案

### 15.1 设计方向

商城 UI 建议采用：

**淘宝式商品流骨架 + Bloom 风格覆盖层**

这意味着：

1. 结构熟悉
2. 页面完整
3. 差异化放在角色互动和氛围层

### 15.2 普通商城区视觉

建议基调：

1. 象牙白
2. 浅灰
3. 暖金
4. 少量柔粉

搜索栏、模式切换、点评浮层可以保留 Bloom 设备感的轻磨砂和玻璃感。

### 15.3 私密专区视觉

私密专区只在内部切换气质：

1. 深可可
2. 酒红
3. 雾黑
4. 暗金

但结构仍然是标准商城，不重新发明布局。

### 15.4 商品卡建议

每张卡最少显示：

1. 商品图
2. 标题
3. 价格
4. 标签
5. 一条角色短评或推荐理由
6. 一个轻交互按钮

卡片的文字层级建议固定为：

1. 第一行：标题
2. 第二行：副标题或标签
3. 第三行：`cardBlurb`
4. 第四行：角色短评或推荐原因

### 15.5 详情页建议

详情页一定要有：

1. 图文主体
2. 推荐原因
3. 配送去向
4. 角色点评
5. 四个底部动作按钮
6. 完整商品描述

完整商品描述建议拆为几个折叠区块：

1. `商品说明`
2. `适合场景`
3. `买完后会去哪`
4. `如果送给TA`

这样既能写得很详细，又不会让页面变成一整块长文。

## 17. 分几批做

建议一共分 **4 批**，不要一口气全做。

### 第 1 批：商城骨架落地

目标：让商城成为一个可进入、可浏览、可下单、可付款、可看订单的独立 App。

必须完成：

1. 首页入口
2. `mall` App 页面挂载
3. 商城首页
4. 搜索和分类
5. 商品详情
6. 购物车
7. 订单页
8. 钱包付款
9. 自购订单
10. `我的物品`

这批不做：

1. 一起逛
2. 角色深度点评
3. 复杂生成补货
4. 节日玩法

### 第 2 批：送礼和角色互动

目标：让商城开始像 Bloom，而不只是普通电商。

必须完成：

1. `送给TA`
2. `问问TA`
3. `分享给TA`
4. 送礼订单状态
5. 送礼记录
6. 礼物反馈

### 第 3 批：共逛与生成货架

目标：让商城变得更活。

必须完成：

1. `一起逛`
2. 陪逛角色选择
3. 本轮货架主题
4. 刷新时受控补货
5. 角色少量点评
6. 搜索意图解析

### 第 4 批：后续与高级玩法

目标：让商城从“能用”走向“有生命力”。

必须完成：

1. 愿望单
2. 节日礼物建议
3. 到货开箱
4. 套装收集
5. 共同空间自动摆放链
6. 动态/论坛外溢玩法
7. 自动提醒和自动推荐

## 18. 每批验收标准

### 第 1 批验收

1. 用户能从首页进入商城
2. 用户能搜索、浏览、下单
3. 钱包能扣款
4. 订单有状态
5. 购买后物品进入正确归属

### 第 2 批验收

1. 用户能把商品送给角色
2. 角色会产生可区分的反馈
3. 商品能分享进聊天
4. 送礼链有完整记录

### 第 3 批验收

1. 一起逛时货架不是死的
2. 角色点评有存在感但不吵
3. 搜索和刷新会受用户选择约束

### 第 4 批验收

1. 商城事件会持续影响其他模块
2. 用户会觉得“买东西有后续”
3. 商城具备自己的可回访理由

## 19. 默认结论

为了避免后续反复讨论，这里先定几个默认结论：

1. 商城必须是独立 App
2. 商城支付统一走钱包
3. 商品购买后不能只写订单，必须进入明确物品归属
4. `Monitor` 只做展示投影，不做主存储
5. `情侣空间` 可以接共同空间类商品
6. 第一批先做标准交易骨架，第二批再强化角色互动
7. 私密专区保留，但以受限独立模式接入，不污染普通货架

---

## 20. 最终建议

商城最稳的落地顺序是：

1. 先把它做成一个完整、好用、独立的购物 App
2. 再把角色互动叠上去
3. 再把共逛、送礼和后续玩法做厚

如果一开始就只做“会说话的商品流”，它会很快变成一个有趣但不完整的半成品。

如果先把交易骨架、支付、订单、物品和配送定清楚，再叠 Bloom 的关系玩法，它就会真正变成这个项目里长期能长、能联动、能复用的一块基础设施。
